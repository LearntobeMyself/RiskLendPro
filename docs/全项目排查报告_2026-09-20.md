## 2. P0 阻断问题

### P0-1 IntelliJ 模块模型损坏，运行命令没有 classpath

**现象**

用户从 IDEA 启动时实际命令为：

```text
java.exe ... org.example.risklendpro.cs.CustomerServiceApplication
错误: 找不到或无法加载主类
```

命令中完全没有：

```text
-classpath
```

**已复现的证据**

IDEA 日志：

```text
Failed to load module configuration from ...\services\cs-service\cs-service.iml:
'url' attribute is missing in 'content' tag

com.intellij.execution.CantRunException: 模块 'cs-service' 没有 JDK
```

工程配置现状：

- `.idea/misc.xml` 开启了外部项目模型：
  ```xml
  <component name="ExternalStorageConfigurationManager" enabled="true" />
  ```
- IDEA 运行时持续重写 `.idea/modules.xml` 和 `.iml`。
- Maven IDEA 插件生成的模块内容缺少 `content url`，且 JDK 名称曾写成 `jbr-21`，项目 SDK 名称实际是 `21`。
- 项目本身编译产物存在：
  ```text
  services/cs-service/target/classes/.../CustomerServiceApplication.class
  services/cs-service/target/cs-service-0.0.1-SNAPSHOT.jar
  ```

**结论**

这不是 JDK、源码或主类本身的问题，而是 IDEA 的模块元数据损坏，导致 IDEA 没有把 Maven 依赖加入运行 classpath。

**推荐彻底修复步骤**

1. 完全关闭 IntelliJ IDEA，避免它继续覆盖工程文件。
2. 备份 `.idea`。
3. 删除以下由 IDE 管理的文件：
   - `.idea/modules.xml`
   - 根目录和各模块下的 `*.iml`
4. 将 `.idea/misc.xml` 中的外部存储改为关闭：
   ```xml
   <component name="ExternalStorageConfigurationManager" enabled="false" />
   ```
5. 删除仅用于旧单体的 `services/legacy-service` 目录或其 `target` 内容。
6. 重新打开项目根目录，在 Maven 工具窗口执行：
   ```text
   Reload All Maven Projects
   ```
7. 等待依赖索引完成，再选择：
   ```text
   RiskLendPro - All Services
   ```
8. 如果 IDE 继续加载旧缓存，使用：
   ```text
   File -> Invalidate Caches / Restart -> Invalidate and Restart
   ```

**临时可用方案**

直接双击已经验证通过的：

```text
F:\RiskLendPro\RiskLendPro\start.bat
```

### P0-2 全量测试首次失败（已修复）

**复现命令**

```powershell
$env:JAVA_HOME = 'F:\IntelliJ IDEA 2025.3.1\jbr'
.\mvnw.cmd test
```

**失败结果**

```text
Tests run: 3, Failures: 0, Errors: 1
UserCreditLimitServiceImplTest.adjustLimit_validChangePersists

```

**原因**

`UserCreditLimitServiceImpl.adjustLimit` 调用：

```java
autoDisbursePendingLoans(userId, creditLimit);
```

该私有方法使用了 `loanMapper.selectList(...)`，但测试类只注入了：

- `UserCreditLimitMapper`
- `LimitAdjustLogMapper`

没有注入：

- `LoanMapper`
- `RepaymentPlanMapper`
- `RepaymentRecordMapper`
- `EmailUtil`
- `UserServiceClient`
- `RiskServiceClient`

因此这是**测试配置缺陷**，不是生产逻辑已经确认崩溃。该问题已在本轮修复。

**修复方向**

为该测试补充依赖 Mock，并将待处理贷款查询默认返回空列表：

```java
@Mock
private LoanMapper loanMapper;
```

测试中需要：

```java
when(loanMapper.selectList(any())).thenReturn(Collections.emptyList());
```

已修复并重新运行：

```powershell

```

## 3. P1 安全问题

### P1-1 JWT 密钥配置实际上没有生效

`JwtConfig` 仍使用硬编码常量：

```java
private static final String SECRET = "MySecretKeyForJWT2024VeryLongAndSafe12345678";
```

它没有读取：

```yaml
security.jwt.secret
```

网关使用配置文件中的密钥，业务服务使用硬编码密钥。一旦通过 `JWT_SECRET` 修改密钥，网关签发的 token 与业务服务校验密钥可能不一致，导致全站 401。

**修复方向**

- `JwtConfig` 使用 `@Value("${security.jwt.secret}")` 或 `@ConfigurationProperties`。
- 启动时校验密钥长度和默认值。
- 测试“网关签发 -> 业务服务校验 -> 受保护接口访问”。

### P1-2 内部接口和上传目录匿名放行

`SecurityConfig` 当前配置：

```java
.requestMatchers("/auth/**", "/admin/login", "/admin/register", "/actuator/health", "/internal/**").permitAll()
.requestMatchers("/upload/**").permitAll()
```

风险：

- `/internal/**` 包含额度、行为分、风控评估等写接口。
- 如果 8081-8084 被公网或局域网直接访问，外部请求可以绕过网关调用内部契约。
- `/upload/**` 允许直接下载上传材料。

**修复方向**

- 内部接口至少增加内部密钥、mTLS 或只监听内网地址。
- `/upload/**` 不应匿名放行，应先鉴权并校验文件归属。
- 生产部署只暴露 gateway，不暴露业务服务端口。

### P1-3 CORS 过宽

当前配置：

```text
allowedOriginPatterns = *
allowCredentials = true
```

这会把“允许携带凭据”和“任意来源”组合在一起，风险较高。

建议改为明确的前端域名白名单，并分离开发/生产配置。

### P1-4 数据库连接明文且关闭 SSL

公共配置连接公网数据库：

```text
47.109.109.231
useSSL=false
allowPublicKeyRetrieval=true
```

这会让数据库流量和凭据传输处于高风险状态。

建议：

- 数据库只允许固定出口 IP。
- 启用 TLS。
- 使用密钥管理或部署环境变量。
- 不在配置文件注释中暴露云主机地址和拓扑信息。---

## 4. P1 架构和一致性问题

### P1-5 跨服务 HTTP 调用仍在数据库事务内

扫描发现多处 `@Transactional` 方法内部直接调用 Feign：

- `BehaviorScoreService.activate/recalculate`
- `RiskAssessmentServiceImpl`
- `AdminRiskQueryServiceImpl`
- `AdminLoanOpsServiceImpl`
- `RepaymentScheduleTask`
- `LoanServiceImpl` 中的部分流程

典型问题：

```java
@Transactional
public void activate(...) {
    loanServiceClient.ensureCreditLimit(...);
    recalculateInternal(...);
}
```

结果：

- 外部 HTTP 超时会长时间占用数据库连接。
- 远程成功、本地事务回滚时会产生跨服务数据不一致。
- 重试时可能重复写入或重复调整额度。

**建议**

- 先完成本地事务并提交，再发送事件或可靠消息。
- 使用 outbox + 异步消费者处理跨服务副作用。
- 对重复消费增加幂等键。

### P1-6 大量异常被静默吞掉

静态扫描发现多处：

```java
catch (Exception ignored) { }
```

主要出现在管理端批量查询、监控聚合和文件存储流程。

影响：

- 远程服务异常时页面可能显示错误或不完整数据，但日志没有上下文。
- 用户看到空值，无法判断是业务为空还是调用失败。
- 风控监控结果可能静默缺失。

**建议**

- 至少记录 `traceId`、远程服务、请求参数摘要和异常类型。
- 对关键数据失败采用 fail-fast，对可选展示数据才允许降级。
- 返回值中增加 `partialData` 或 `dataStatus`。

### P1-7 管理端存在 N+1 和逐条远程调用

典型位置：

- `AdminRiskQueryServiceImpl`
- `AdminLoanQueryServiceImpl`
- `AdminRepaymentQueryServiceImpl`
- `AdminUserServiceImpl`
- `InternalLoanController.getLoanBehavior`
- `RepaymentScheduleTask`

部分实现先循环用户/贷款，再逐条查询或逐条 Feign 调用。

影响：

- 用户列表、B 卡监控和大屏接口延迟高。
- 远程服务抖动时会放大超时。
- 监控数据可能因为部分逐条调用失败而不一致。

**建议**

- 先批量取 ID，再一次性查询。
- 增加批量 Feign 契约和批量 Mapper 方法。
- 对分页数据限制最大页大小。

### P1-8 旧 `legacy-service` 产物仍残留

根 `pom.xml` 已不再包含 `legacy-service`，该目录也没有源码和 `pom.xml`，但仍有：

```text
services/legacy-service/target
services/legacy-service/legacy-service.iml
```

影响：

- IDEA 可能重新识别为旧模块。
- 旧 class 文件和旧配置会造成“类已存在/类找不到”的混乱。
- 旧的 `application.yml` 中可能继续留存密钥。

**建议**

- 关闭 IDEA 后删除整个 `services/legacy-service` 目录。
- 同时清理 `.idea/modules.xml` 和 `*.iml` 中的旧模块引用。

### P1-9 端口和入口与旧文档认知不一致

当前实际端口：

| 服务 | 端口 |
|---|---:|
| user-service | 8081 |
| risk-service | 8082 |
| loan-service | 8083 |
| cs-service | 8084 |
| gateway | 8088 |

旧脚本和旧文档曾使用：

```text

```

虽然 README 和 `start.bat` 已更新，但如果团队仍从旧 IDEA 配置或旧命令启动，会继续命中错误入口。

## 5. P2 构建、依赖和质量问题

### P2-1 测试覆盖严重不足

扫描结果：

```text
主代码 Java 文件：194
测试 Java 文件：6
```

现有测试主要集中在：

- 还款计算
- 部分还款服务
- 部分 B 卡特征
- 部分行为分逻辑

缺少：

- Controller 鉴权测试
- 网关路由测试
- 内部接口防越权测试
- 数据库迁移测试
- 多服务启动集成测试
- B 卡历史 as-of 测试
- 模型规则加载/切换测试
- 跨服务失败补偿测试

### P2-2 依赖声明不完整

`mvnw.cmd -DskipTests dependency:analyze` 在多个模块报告：

- 使用未声明依赖
- 声明未使用依赖
- 直接依赖传递依赖中的 API

这不一定会立刻导致编译失败，但会使升级 Spring Boot、MyBatis 或网关版本时出现隐蔽破坏。

建议：

- 直接使用的 API 必须在模块 `pom.xml` 中显式声明。
- 公共依赖通过父 POM 的 `dependencyManagement` 统一版本。
- 定期运行 `dependency:analyze` 并处理真实告警。

### P2-3 异常类型不统一

大量业务校验使用：

```java
throw new RuntimeException("...");
```

导致：

- HTTP 状态码不稳定。
- 全局异常处理难以区分 400、403、404、409 和 500。
- 前端难以做不同处理。

建议定义：

- `BusinessException`
- `NotFoundException`
- `ForbiddenException`
- `ConflictException`
- `ValidationException`

### P2-4 日志级别和 MyBatis SQL 输出过重

公共配置：

```yaml
mybatis-plus:
  configuration:
    log-impl: org.apache.ibatis.logging.stdout.StdOutImpl

logging:
  level:
    org.example.risklendpro: debug
```

风险：

- 生产日志泄露 SQL 和业务数据。
- 大量标准输出影响性能。
- 与结构化日志系统不兼容。

建议生产环境关闭 `StdOutImpl`，使用参数化 SQL 日志和脱敏。

## 6. 风控模型问题摘要

详细阶段任务见：

```text
docs/风控模型问题诊断与B卡AI阶段修改指南.md
```

### P0-1 不可信 B 分仍可能进入额度系数

`InternalRiskController.getLimitMultiplier` 直接调用：

```java
behaviorScoreService.resolveLimitMultiplier(score)
```

不会检查：

- `scoreReliable`
- `dataStatus`
- 模型版本
- 特征版本

虽然自动调额当前默认关闭，但一旦开启就有风险。

### P0-2 准时还款后 B 分不会及时重算

正常还款服务没有触发 B 分重算，重算主要发生在：

- 激活 B 卡
- 逾期定时任务
- 手动管理接口

因此准时还款的正面行为可能长期不反映在 B 分中。

### P0-3 历史 B 卡快照存在时间穿越

`BCardFeatureServiceImpl.buildFeatureVector` 目前会读取：

- 当前贷款状态
- 当前还款计划状态
- 当前 `overdueDays`
- 当前额度

即使传入 `asOfDate`，也没有完整按历史时点还原。直接回填训练集会产生未来信息泄漏。

### P0-4 训练与在线缺失值不一致

Python 清洗阶段将缺失值填为 `0`，训练阶段使用中位数填充，Java 在线又无法区分“真实 0”和“缺失”。

这会导致：

- 离线指标无法复现
- 线上分数偏离训练分布
- 缺失用户被错误识别为可信用户

### P0-5 标签和时间切分不成立

当前 B 卡训练：

- 使用 Home Credit `TARGET`
- 随机切分训练/测试
- 没有真实观察期/表现期
- 数据缺失时会回退到合成数据

这不属于可用于生产 B 卡的标签体系。

### P1-1 V1 模型性能偏弱

当前记录：

```text
AUC ≈ 0.5713
KS  ≈ 0.1236
Top 20% 坏客户抓捕率 ≈ 26.8%
```

适合监控参考，不适合自动降额。

### P1-2 PDO 未真实校准

模型使用 `class_weight=balanced`，再基于预测 odds 做 PDO 标定。当前 `target_odds` 约 `0.904`，而训练数据实际违约率约 `8.72%`，两者不是同一概率口径。
