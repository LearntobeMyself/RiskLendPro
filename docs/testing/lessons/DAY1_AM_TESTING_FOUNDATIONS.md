# 第一部分：90 分钟测试基础

## 1. 测试、质量保障与测试开发

### 1.1 软件测试

软件测试不是“运行程序，看有没有报错”，而是：

> 使用明确的依据，对软件及其相关工作产品进行评估，发现实际结果与期望结果之间的差异，并为质量决策提供证据。

这里有四个关键词：

- **依据**：需求、业务规则、接口契约、法规、风险、不变量。
- **评估对象**：代码、接口、数据库、配置、文档、架构设计、运行指标。
- **差异**：错误结果、遗漏行为、不一致、性能不足、安全风险、不可恢复状态。
- **证据**：可复现步骤、请求响应、日志、数据库状态、测试报告、监控指标。

RiskLendPro 示例：

- 文档规定自动通过阈值是 788，但代码默认值是 720。
- 程序能够正常运行，不代表行为正确。
- 测试需要证明 720–787 这一批用户是否会被错误自动通过。

### 1.2 质量保障（QA）

测试关注产品当前是否符合预期；质量保障还关注：

- 为什么这个缺陷能够进入代码？
- 需求评审是否遗漏了验收标准？
- 是否缺少代码评审、自动化测试、发布门禁或线上监控？
- 同类问题以后如何更早、更便宜地被阻止？

发现阈值漂移只是测试；进一步将阈值收口到单一配置源、补边界自动化、在 CI 中阻断回归，才是质量保障。

### 1.3 测试开发（SDET）

测试开发使用开发能力解决质量问题，常见工作包括：

- 开发自动化测试和测试框架。
- 构造稳定、可重复的测试数据和环境。
- 编写质量工具、Mock 服务、流量回放、故障注入和报告系统。
- 阅读业务代码、数据库和日志，定位根因而不是只提交现象。
- 把高风险场景放进 CI/CD 发布门禁。
- 建立线上监控、回归策略和质量度量。

测试开发不是“开发能力弱一点的后端”，也不是“只写脚本的功能测试”。

你在面试中的定位：

> 我使用 Java 后端能力理解调用链、事务和数据一致性，再通过自动化、并发测试和质量门禁降低系统风险。

## 2. 验证与确认

### Verification：是否按照规格正确构建

常见对象：

- 需求是否无歧义。
- API 是否符合契约。
- 状态迁移是否符合设计。
- 代码是否正确实现评分规则。

示例：代码是否严格按照 788/642 规则分类？

### Validation：构建的东西是否真正满足用户和业务需要

示例：

- 评分通过线即使实现正确，是否真的符合风险策略？
- 用户通过评估后额度迟迟不到账，流程是否可接受？
- 还款成功但可用额度没有恢复，用户是否能继续使用产品？

一句话区分：

- Verification：做得对不对。
- Validation：做的是不是正确的事情。

## 3. 七条测试原则

### 3.1 测试只能证明缺陷存在，不能证明缺陷不存在

100 个用例通过，只能说明这 100 个条件下没有发现问题。

RiskLendPro 即使所有现有单测通过，也没有验证：

- 网关是否真的返回 401/403。
- 两个借款请求并发时是否会超额。
- Feign 超时后风控和额度是否一致。
- 定时任务与主动还款同时运行时是否会重复恢复额度。

### 3.2 穷尽测试不可能

输入、状态、角色、服务故障和并发时序的组合接近无限。

因此需要：

- 等价类与边界值减少重复组合。
- 风险驱动决定优先级。
- 决策表覆盖关键规则组合。
- Pairwise 控制组合爆炸。

### 3.3 尽早测试

发现需求阈值不一致的成本远低于放款后发现错误授信。

测试应参与：

- 需求评审。
- 架构和接口设计。
- 数据库设计。
- 代码评审。
- 上线前验证和上线后监控。

### 3.4 缺陷具有聚集性

少数复杂、高变更、高耦合模块往往包含大部分缺陷。

RiskLendPro 高风险聚集区：

- `RiskAssessmentServiceImpl`
- `CreditScoreEngineImpl`
- `LoanServiceImpl`
- `RepaymentServiceImpl`
- 网关与内部接口鉴权

### 3.5 杀虫剂悖论

一直重复同一批用例，发现新缺陷的能力会下降。

改进方式：

- 根据线上事故和代码变更补新用例。
- 增加并发、故障、权限和数据一致性场景。
- 定期评审过时用例。

### 3.6 测试依赖上下文

金融系统与普通内容展示系统的测试重点不同。

金融/交易系统优先关注：

- 资损
- 幂等
- 事务和一致性
- 权限与隐私
- 审计
- 故障恢复

### 3.7 没有缺陷不等于产品成功

如果需求本身错误、流程不可用或性能无法接受，即使代码完全符合错误规格，产品仍然失败。

## 4. 静态测试与动态测试

### 静态测试

不运行程序也能发现问题：

- 需求评审
- 设计评审
- 代码评审
- 文档检查
- 静态代码分析

本项目已经通过静态检查发现：

- 文档阈值 788/642 与代码 720/580 不一致。
- README 和启动脚本指向不存在的 `legacy-service`。
- 默认配置包含不应进入仓库的敏感值。

### 动态测试

运行被测对象：

- 单元测试
- API 测试
- 数据库集成测试
- 性能测试
- 安全测试
- 端到端测试

结论：优秀测试开发不能只会运行接口，也要能通过阅读提前发现问题。

## 5. 测试层级

### 5.1 单元测试

对象：函数、类或小组件。  
特点：快、稳定、定位准确，通常隔离数据库和网络。

本项目示例：

- `RepaymentCalculatorTest`
- `AdminPathAccessTest`

适合发现：

- 金额计算错误
- 边界值错误
- 纯规则判断错误

不能独立证明：

- HTTP 安全过滤器生效
- SQL 与 MySQL 兼容
- 事务和锁正确
- 跨服务调用成功

### 5.2 集成测试

验证多个真实组件的协作：

- Java 服务 + MySQL
- Service + Mapper
- Gateway + Security
- Feign 客户端 + HTTP 契约

适合发现：

- SQL、索引和事务错误
- Spring 配置错误
- 序列化错误
- 服务契约不一致

### 5.3 系统测试

验证完整系统是否满足功能和非功能需求。

示例：

- 用户注册到还款的完整业务流程。
- 不同角色的完整权限矩阵。
- 系统在下游超时情况下的行为。

### 5.4 验收测试

从业务或用户角度判断是否可以交付。

示例：

- 风控策略人员确认评分与审批规则。
- 财务确认额度与还款账务正确。
- 运营确认管理页面和流程可使用。

---

## 6. 测试类型

### 功能测试

系统是否做了应该做的事。

### 非功能测试

系统做得是否足够好：

- 性能
- 安全
- 可靠性
- 可恢复性
- 易用性
- 兼容性

### 黑盒测试

不依赖内部实现，根据输入输出和业务规则设计。

例：提交 788 分用户，预期自动通过。

### 白盒测试

根据分支、条件、调用和内部数据流设计。

例：阅读代码后发现“黑名单三级命中”会提前返回，因此应断言评分引擎后续方法没有被调用。

测试开发通常同时使用黑盒和白盒视角。

## 7. 测试生命周期

### 7.1 需求分析

回答：

- 测什么？
- 正确结果是什么？
- 哪些规则有歧义？
- 哪些失败最危险？

### 7.2 测试计划

确定：

- 范围与不测范围
- 人员和时间
- 环境与数据
- 测试层级
- 准入、准出和风险

### 7.3 测试分析与设计

将需求转为：

- 测试条件
- 测试场景
- 测试用例
- 测试数据
- 自动化策略

### 7.4 实现与执行

- 搭建环境
- 编写自动化
- 执行用例
- 收集日志、请求、响应和数据库证据

### 7.5 缺陷管理

一个合格缺陷至少包含：

- 清晰标题
- 环境和版本
- 前置条件
- 复现步骤
- 实际结果
- 期望结果
- 影响范围和优先级
- 日志、截图、请求响应或数据库证据

### 7.6 报告与关闭

报告不只是“通过率 95%”，还要回答：

- 剩余风险是什么？
- 哪些范围没有测试？
- 失败是否阻断发布？
- 是否需要灰度、回滚和监控？

## 8. 风险驱动测试

简单风险模型：

```text
风险优先级 = 影响程度 × 发生概率 × 难以发现程度
```

不用纠结精确数学，关键是比较顺序。

### RiskLendPro 示例

| 风险 | 影响 | 概率 | 难探测 | 优先级 |
|---|---:|---:|---:|---|
| 同一申请重复授信 | 5 | 3 | 4 | P0 |
| 并发还款重复恢复额度 | 5 | 3 | 5 | P0 |
| 普通用户访问管理接口 | 5 | 2 | 4 | P0 |
| 产品图片偶尔不显示 | 2 | 3 | 2 | P2 |
| 邮件文案标点错误 | 1 | 3 | 1 | P2 |

测试时间不足时，不是简单“少测一点”，而是：

1. 先保资损、权限和核心交易链路。
2. 再测高变更、高复杂度和历史高缺陷模块。
3. 对低风险展示功能做抽样或延后。
4. 明确汇报未覆盖范围和残余风险。

# 第二部分：75 分钟 JUnit 代码阅读

## 9. 单元测试基本结构

推荐 Arrange-Act-Assert：

```java
@Test
void zeroRate_shouldGenerateScheduleWithoutInterest() {
    // Arrange：准备输入
    BigDecimal principal = new BigDecimal("10000");
    BigDecimal rate = BigDecimal.ZERO;

    // Act：执行被测行为
    List<RepaymentDetail> details =
            RepaymentCalculator.calculateEqualPrincipalAndInterest(principal, rate, 12);

    // Assert：验证业务结果与不变量
    assertEquals(12, details.size());
    assertTrue(details.stream()
            .allMatch(detail -> detail.getInterest().compareTo(BigDecimal.ZERO) == 0));
}
```

需要识别：

- **SUT**：System Under Test，被测对象。
- **输入**：参数和前置状态。
- **行为**：执行的方法。
- **Oracle**：判断正确与否的依据。
- **断言**：把 Oracle 写成机器可验证的条件。

## 10. 阅读 `RepaymentCalculatorTest`

文件：

`services/loan-service/src/test/java/org/example/risklendpro/loan/repay/RepaymentCalculatorTest.java`

按顺序完成：

1. 找出每个测试的 SUT、输入、行为和断言。
2. 标记哪些断言验证具体结果，哪些验证业务不变量。
3. 回答为什么本金总和比“第一期金额等于某个固定值”更稳定。
4. 找出以下边界是否已有覆盖：
   - 零利率
   - 零本金
   - 负本金
   - 0 期
   - 负期数
   - 1 期
   - 极大本金
   - 超高利率
   - `null`
5. 判断是否可以用参数化测试减少重复。

### 观察重点

好的地方：

- 测了零利率回归。
- 测了多种还款方式。
- 使用本金总和、不为负等不变量。

可改进处：

- 多个非法输入放在一个测试里，失败时定位不够精确。
- 还缺少 `null`、负利率、极大数值和舍入边界。
- 部分测试只验证局部性质，未验证每期金额之和或最终尾差。

## 11. 阅读 `AdminPathAccessTest`

文件：

`common-api/src/test/java/org/example/risklendpro/api/security/AdminPathAccessTest.java`

按顺序完成：

1. 写出角色×路径×方法的决策表。
2. 找出“允许”和“拒绝”场景是否成对出现。
3. 判断哪些测试可以参数化。
4. 回答：这些测试全部通过，能否证明真实 HTTP 请求一定返回 403？

正确答案：不能。

原因：

- 它只调用了一个纯 Java 权限判断函数。
- 没有经过 Gateway Filter。
- 没有解析 JWT。
- 没有经过 Spring Security。
- 没有验证Controller上的方法级权限。

这说明单元测试有价值，但不能替代更高层测试。

# 第四部分：自测题

先回答，再看答案。

1. 500 个用例全部通过，是否能证明系统没有缺陷？
2. 发现需求文档和代码阈值不同，属于静态测试还是动态测试？
3. Mockito 单元测试能否证明 MySQL 的 `FOR UPDATE` 正确工作？
4. 用户接口返回 200，但数据库额度被扣了两次，测试是否通过？
5. 为什么不能在测试中直接使用项目默认公网数据库？
6. `AdminPathAccessTest` 通过后，为什么还需要 MockMvc/WebTestClient？
7. 测试时间不足时应该随机删掉一半用例吗？

## 参考答案

1. 不能，只能说明已执行条件下没有发现缺陷。
2. 静态测试，因为无需运行程序。
3. 不能，需要真实 MySQL 集成/并发测试。
4. 不通过，HTTP只是表面结果，数据库不变量被破坏。
5. 数据不可控、不可重复、可能破坏真实数据、泄漏凭据并产生误报。
6. 需要验证真实JWT解析、过滤器链、Spring Security和HTTP状态。
7. 不应该；应按业务影响、发生概率、变更和历史缺陷做风险排序。
