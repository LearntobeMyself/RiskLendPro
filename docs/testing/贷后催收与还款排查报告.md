## 二、本次确认并修复的 Bug（6 个）

### BUG-C1（严重）"提前3天还款提醒"邮件是永远不可达的死代码

- **位置**：RepaymentScheduleTask.checkAndUpdateActivePlan
- **现象**：接口文档承诺"还款到期前3天发送邮件提醒"，但该邮件从未发出过。
- **根因**：提醒判断写成 `diffDays == 3`（到期**后**3天）；而当 diffDays >= 1 时计划已被置为 OVERDUE、离开 ACTIVE 扫描集合，因此 `== 3` 分支在逻辑上永远走不到。
- **影响**：用户收不到提前提醒，逾期率与客诉风险上升；文档与实现不一致。
- **修复**：条件改为 `diffDays == -3`（commit `a75e248`），并有新增测试 reminderEmailSentThreeDaysBeforeDue 覆盖。

### BUG-C2（严重）逾期识别随放款时刻漂移，最长延迟近 1 天

- **位置**：RepaymentScheduleTask L115-116、L149-150
- **现象**：14:32 放款的借据，到期次日 01:00 扫描时 diffDays=0 不判逾期，要到再往后超过放款时刻才算逾期 1 天。
- **根因**：天数差用毫秒截断 `(today - dueDate) / 86400000` 计算，而 dueDate 由 `Calendar.getInstance()` 生成、含放款时刻的时分秒。
- **影响**：逾期认定、首逾邮件（diffDays==1）、M1/M2/M3/M4 的 30/60/90 天等级边界全部随放款时刻漂移，行为不确定。
- **修复**：新增 `daysSinceDue()` 按自然日计算（LocalDate + ChronoUnit.DAYS.between，忽略时分秒），两处替换（commit `a75e248`）。

### BUG-C3（严重）用户服务异常导致逾期状态机整体停摆

- **位置**：RepaymentScheduleTask.checkAndUpdateActivePlan L110-113
- **现象**：`userServiceClient.getUser()` 返回 null 时直接 return，且该调用在计算 diffDays **之前**。
- **根因**：逾期落库（记录/计划/借据状态、hasOverdue、B 卡重算）本不依赖用户信息，只有发邮件依赖；代码却把取用户放在了所有逻辑前面。
- **影响**：用户服务抖动期间，到期该转逾期的不转、该累计的逾期天数不累计，且每日任务静默跳过，事后无补偿。
- **修复**：逾期判定与落库前移至取用户之前；user 仅在发邮件前获取，取不到/异常仅跳过邮件并 log.warn（commit `a3663d3`），新增测试 overduePersistedEvenWhenUserUnavailable 覆盖。

### BUG-C4（中）首逾处理非原子，中断后 hasOverdue 永久缺失

- **位置**：RepaymentScheduleTask.handleOverdue + updateOverduePlan
- **现象**：若 markLoanOverdue 之后、额度标志更新之前/之中发生异常，计划已是 OVERDUE；次日重试走 updateOverduePlan 分支，该分支不补额度标志。
- **根因**：逾期标志（hasOverdue/overdueAmount）采用增量累加且无自愈路径；OverdueLimitAdjustTask 按 `has_overdue=true` 扫描调额。
- **影响**：该用户永远不会被逾期调额任务命中，首逾邮件也不补发，风控降额失效。
- **修复**：新增 OverdueStateSync 组件（见下），逾期分支每日自愈调用（commit `08610d0`）。

### BUG-C7（中）老数据 overdue_amount 为 NULL 时首逾 NPE

- **位置**：RepaymentScheduleTask.updateUserCreditLimit（已删除）
- **现象**：`creditLimit.getOverdueAmount().add(...)` 在 overdue_amount 为 NULL 的老数据上直接 NPE，进而触发 BUG-C4 的中断路径。
- **修复**：OverdueStateSync 改为重算覆盖写（不再增量累加），天然规避 NULL 累加（commit `08610d0`）。

### BUG-R1（中）还款后逾期金额不重算，长期虚高

- **位置**：RepaymentServiceImpl.refreshOverdueState（原 L197-213）
- **现象**：用户有多笔逾期计划时，还清其中一笔后 `hasOverdue=true` 保持，但 `overdueAmount` 不扣减。
- **根因**：原逻辑只在"逾期计划数 == 0"时清零，">0"时仅置标志位不重算金额。
- **影响**：用户逾期金额虚高，影响展示与依赖该字段的风控判断。
- **修复**：refreshOverdueState 整块替换为 OverdueStateSync 调用，按事实源（全部 OVERDUE 计划下 OVERDUE 记录求和）幂等回写（commit `08610d0`）。

### BUG-C5（中）逾期调额任务事务内含 Feign + 行锁，单用户失败整批回滚

- **位置**：OverdueLimitAdjustTask.autoAdjustOverdueUserLimit
- **现象**：方法级 `@Transactional` 包裹整个批处理循环，循环内含 Feign 调用（recalculateBehaviorScore / getLimitMultiplierForUser）与 `FOR UPDATE` 行锁。
- **根因/影响**：违反项目约束"事务边界不得包含 Feign 调用"——长事务占用数据库连接与行锁，Feign 慢调用放大锁竞争；且任一用户处理异常导致**当夜所有用户**调额回滚失效。
- **修复**：删除方法级事务，改为每用户 TransactionTemplate 独立提交；Feign 调用移至事务外；单用户异常 log.warn 跳过；删除 B 卡分支冗余的二次锁读（commit `9175175`，测试适配 `c0cf029`）。
