# 综设 III：要做到「比较好」（≥85 优）至少完成什么

> **课题**：多数据源融合的互联网个人贷款风控系统（互联网+金融）  
> **依据**：  
> 1. 电子科技大学《进阶式挑战性综合项目 III 课题任务书》  
> 2. 李美蓉《项目导引与需求分析》  
> **对照代码**：当前仓库 RiskLendPro（综设 II 单体 Spring Boot + Python 评分卡）  
> **目标口径**：优（≥85），不是「能演示就行」  
> **文档版本**：v1.1｜2026-09-01  
> **配套**：代码缺口与三人后端拆分见 [综设III代码缺口与三人后端计划.md](./综设III代码缺口与三人后端计划.md)

## 0. 先看结论

任务书把分数档写死了。要做到比较好，**不是比良多做几个模块**。

1. **良和优的功能清单相同**：扩展模块必须全部做完，必须微服务重构，必须大模型客服，必须 ≥2 种测试，联调还必须全过。  
2. **优比良多出来的，几乎只有两件事**：  
   - 智能风控模型效果 **不低于综设 II 评分卡**（当前 A 卡 AUC≈0.714 为底线）；  
   - 文档不仅「符合规范」，还要 **内容清晰可读**。  
3. **中（60–75）** 也要求模块全做 + 微服务 + 大模型 + 2 种测试，只允许 **≤2 个模块测试未通过**。  
4. 缺任一扩展、不做微服务、客服不调大模型、测试方法不够、或 **>2 个模块测不过** → 直接差（<60）。

**策略**：按良的功能范围一次性做满，再把模型效果和文档质量拉到优。不要把学期花在把综设 II 单体打磨得更漂亮上。

课件本周立刻要交的四项（见第 11 节）：综设 II 能跑；已有功能/问题/是否重构清单；**功能结构图**；小组分工 + 本阶段实施计划。

## 5. 七个扩展方向：最小可验收口径

课件要求「全部设计开发实现」，不是调研报告。下面是课程能演示、文档能写清、联调能跑通的下限。不要做成银行生产系统。

### 5.1 多模型智能风控（最高优先级，优的关键）

要解决的问题：多个风险模型、规则与决策策略如何协同。

1. **规则引擎**（硬规则，先于模型）：年龄、黑名单 L3、身份核验失败、多头申请等 → 直接拒或转人工。  
2. **申请模型 A 卡**：沿用综设 II（WOE+LR+PDO），**AUC 不得低于现有约 0.714**，训练日志留证。  
3. **行为模型 B 卡**：放款后按周期打分，用于观察/降额，不参与贷前硬拒。  
4. **至少一个对比/辅助模型**（满足「多模型」叙事）：例如 XGBoost 离线训练，仅输出风险等级或概率，**不替代 A 卡作为主解释模型**。  
5. **决策中枢**：规则 → A 卡 →（可选）辅助模型投票/加权 → 策略表（通过 / 复核 / 拒绝 + 额度档）。  
6. **模型管理**：版本、`is_active`、切换、回滚（综设 II 已有规则表，做成管理端页面）。

详细设计里必须有「为何主卡仍用评分卡、辅助模型如何接入」的方案对比（对应任务书「选出最优流程」）。

答辩一句话：不是再训练一个更黑的模型，而是规则 + A 卡 + B 卡 + 策略表协同；主模型效果不低于综设 II。

**不要**为了「多模型」把主卡换成不可解释、还更差的深度模型。良只要「跑得通」；优要效果不低于综设 II。

### 5.2 贷中管理与监控（高）

- 放款成功后进入观察池。  
- 定时任务：逾期天数、额度使用率、B 卡分数、近期还款行为。  
- 三级动作：正常观察 / 预警（站内信或邮件） / 降额或限制支用。  
- Web 管理端：监控列表、预警详情、人工处置。  
- 演示数据：至少 1 个正常户、1 个预警户、1 个降额户。

### 5.3 贷后管理（高）

- 贷款状态机：放款中 → 还款中 → 逾期 → 催收中 → 结清（可选核销）。  
- 还款计划 + 实还记录（已有基础，补逾期罚息或宽限期说明即可）。  
- 催收任务：逾期自动生成工单，管理员记录催收结果。  
- 结清后释放额度。

### 5.4 客服支持（中优先级，但是差档一票否决）

- Android/Web 用户可对话。  
- **必须**调用第三方大模型（通义千问 / DeepSeek / 讯飞等），不要只做本地关键词。  
- 工单：用户转人工 → 管理员处理 → 状态回写。  
- 范围限制：只答产品、还款、进度、材料；敏感决策（为何被拒）给标准话术，不让模型乱编。  

未调第三方大模型 API，直接不符合中/良/优。

### 5.5 消费贷 / 多种贷款产品（高）

独立产品：期限、利率、额度上限、风控策略可配置；每条申请必须带 `productId`。

建议至少 2 种（消费贷必做）：

| 产品 | 差异点（必须能看出来） |
|------|------------------------|
| 消费贷（必做） | 期限、利率、额度上限、A 卡策略档 |
| 现金贷/应急贷（建议） | 更短期限、更严规则 |
| 循环额度（可选，可复用现有额度体系） | 一次授信、多次支用 |

不能所有产品同一套阈值却假装是多产品。

### 5.6 获客（中）

选 2～3 个即可：

- 产品展示 / 活动落地页（Android 首页或 Web）。  
- 邀请码或渠道号，注册时写入 `channel`。  
- 管理端：渠道转化漏斗（曝光/注册/完件/通过，演示数据即可）。  

不要做真实投放。爬虫继续服务风控数据源（黑名单），获客不必靠爬虫拉客。

### 5.7 安全管理（高，贯穿全程）

- 网关统一鉴权；用户端与管理端权限分离。  
- 接口限流（高并发叙事的一部分）。  
- 敏感字段脱敏（身份证、手机号）。  
- 操作审计日志（审批、调额、催收）。  
- HTTPS 或至少文档说明部署证书；JWT 过期与刷新。  
- 风控/征信库不直接暴露给借款端。

## 6. 微服务怎么拆才像课设、又能写进优

不要拆 10 个服务。建议 **1 网关 + 4 业务服务 + 公共组件**，能讲清边界即可。

```
                    Android借款端          Vue管理端
                           │                  │
                           └────────┬─────────┘
                                    ▼
                         Spring Cloud Gateway
                         （鉴权、限流、路由）
                                    │
          ┌────────────┬────────────┼────────────┬────────────┐
          ▼            ▼            ▼            ▼            ▼
     用户认证服务   产品获客服务   风控决策服务   信贷账务服务   客服工单服务
     (JWT/用户)    (产品/渠道)    (规则/A/B卡)   (申请/放款/     (大模型/
                                   + 模型管理     还款/贷中贷后)   工单)
          │            │            │            │            │
          └────────────┴──── Redis / MySQL / 注册中心 ─────────┘
                                    │
                          Python 离线训练（批任务）
                          只写征信库，不直接对外
```

产品获客可并入账务或用户服务（变成 1 网关 + 4 服务），报告里写清边界即可。

**拆分原则（答辩用）**：

- 风控服务无状态，规则热更新。  
- 账务服务管钱和状态机，事务在本服务内。  
- 客服独立，避免大模型超时拖垮审批。  
- 网关承担高并发入口（限流、熔断）。  

**高并发 / 高性能部署最小证据**：

- Gateway 限流 + Redis 缓存评分报告（综设 II 已有缓存思想）。  
- 风控评估可异步：申请入库 → 消息队列/线程池评估 → 客户端轮询（综设 II 已有 status 轮询，可升级）。  
- Docker Compose 或同等一键启动。  
- **JMeter**：核心接口 P95、QPS 一张图（哪怕并发 50～100）。没有压测图，高并发只能空讲。

## 7. 两端产品：最低演示路径

### 7.1 Android 借款端（必须能操作）

一条用户路径：

1. 注册/登录（可带邀请码）  
2. 浏览产品 → 选消费贷申请  
3. 填写资料 / 上传补充材料  
4. 看风控进度与额度  
5. 支用 → 看还款计划 → 模拟还款  
6. 逾期提示  
7. 打开客服（大模型）→ 必要时转人工  

Web 用户端 SPA 可作为联调辅助，**不能替代 Android 作为任务书借款端交付物**。

## 9. 测试：至少 2 种，建议直接做 3 种

## 12. 答辩演示脚本（按这个练，就是「全功能」）

4. **智能风控**：展示规则命中或 A 卡明细（可解释）。

6. **贷中**：B 卡预警 → 管理员降额。

8. **逾期+贷后**：另一个账号逾期 → 催收工单。  
9. **客服**：问「怎么还款」走大模型；再转一次人工工单。  
10. **安全口播**：网关鉴权、脱敏、限流各展示 1 个失败/成功对比。  

另备 2 个风控反例：黑名单拒绝、低分拒绝。这是综设 II 的家底，不能丢。
